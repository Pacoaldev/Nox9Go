# Changelog

## [1.1.8] - Unreleased

### Features
- **Combo flow maps one whole panel per combo in use.** The Combo flow view merged every combo into a single map, so watching two combos at once was impossible. It now renders one complete panel per combo — its own frame and its own header — two-up from `md` up and full width while only one combo is live, both stretched to the same height by the grid. `liveComboNames` decides which combos deserve a panel: every combo with a request in flight, then every combo whose result is still inside the shared `RECENT_WINDOW_MS` window, de-duplicated case-insensitively and keeping the first spelling the usage stream reported (`web/src/components/analytics/comboMatch.ts`). Panels are ordered by the combo list rather than by first appearance, so a panel never changes column when a sibling combo starts or finishes, and `ComboFlowCard` takes a new optional `comboName` prop — without it it still picks the live combo by itself (`web/src/components/analytics/ComboFlowCard.svelte`, `web/src/components/analytics/ComboFlowView.svelte`, `web/src/components/analytics/comboMatch.test.ts`, `web/public/i18n/literals/es.json`).
- **Role-based routing profiles: stable `pi-*` aliases and an `X-Nox-Role` request header.** A `modelAliases` entry whose target carries no `/` is now resolved as a combo name, so `pi-light`/`pi-work`/`pi-plan` can name the role combos while their members stay editable in the dashboard without touching any client configuration; previously a slash-less target was dropped in the alias branch, so such an alias silently did nothing (`internal/handlers/chat/resolution.go`). Chat requests may now declare `X-Nox-Role: light | work | plan` to select `Combo-Light`/`Combo-Work`/`Combo-Plan` ahead of the body's `model`, so an auxiliary panel or a Pi subagent can name its role without changing the model id it sends; the per-key model policy is enforced against the forced combo as well, and an unrecognized value is ignored rather than rejected (`internal/handlers/chat/chat.go`, `internal/handlers/chat/resolution_alias_combo_test.go`, `internal/handlers/chat/role_header_test.go`).
- **A combo declares the context window it advertises.** A combo published the smallest window any of its seats could serve, so a combo whose seats are mostly 1M but include one 200k seat made a client read a session the 1M seat answered as several times fuller than it was, and auto-compaction fired early. The operator now declares the number instead: `combos.contextWindow` (additive column, `INTEGER DEFAULT 0`), exposed as the JSON field `contextWindow` by the combo reads, accepted by `POST /api/combos` and `PUT /api/combos/{id}`, and refused with `400` when negative or above `100000000` — a refused value leaves the stored row unchanged, and an absent field means the edit says nothing about the window, so an unrelated combo edit never clears one. `0` is the default and publishes exactly what it published before, the derived minimum, so no existing combo changes number; a declared value is published at the top level and in the capability block of `GET /v1/models` and reaches the Pi `models.json` mirror through the same result, while `max_completion_tokens` stays derived from the seats (`internal/db/schema.go`, `internal/db/combos.go`, `internal/handlers/dashboard/combos.go`, `internal/handlers/chat/models_list.go`, `web/src/components/combos/CreateComboModal.svelte`, `web/public/i18n/literals/es.json`).

### Fixes
- **Combo strategy is documented by what the code does, including where a strategy cannot be stored at all.** `capacity` and `fallback` share one branch: members come back in declared order and are never rotated, with no quota or `:free` awareness of their own — cooldown and learned-ceiling filtering live in the combo fallback loop and the quota learner, never in the strategy. A per-combo `strategy` is **not** persisted anywhere: the `combos` row has no such column and `CreateCombo`/`UpdateCombo` discard the error of their `UPDATE combos SET strategy = ?`, so the strategy a combo actually runs comes from the global default or from the per-combo override held in `settings.comboStrategies` (`docs/ARCHITECTURE.md`, `internal/db/dashboard.go`).
- **The Pi model catalogue is no longer published from a half-started gateway.** The startup hook ran `SyncPiCatalog` concurrently with the loops that populate the catalogue, so a read that failed wrote a short model list over `~/.pi/agent/models.json` — valid JSON, no error anywhere, and every combo and model gone from Pi. The sync now reports a read it depends on failing and publishes nothing in that case, and startup retries it every 500ms within a 30s budget, leaving the previous file untouched and logging the reason when no clean read ever arrives (`internal/handlers/chat/models_list.go`, `internal/app/pi_catalog_sync.go`, `internal/app/server.go`). Its tests redirect the package home into a temp directory first, because booting the package otherwise rewrites the developer's real Pi catalogue from a temporary database (`internal/app/hermetic_test.go`).

## [1.1.7] - 2026-11-25

### Features
- **FastRouter joins the recurring free-tier providers.** Synced from `BUSCAPIsPro`, `fastrouter` (`https://api.fastrouter.ai/api/v1/chat/completions`, `Authorization: Bearer`) is registered in `KnownProviders` with its `fr` alias, live `/v1/models` discovery (`https://api.fastrouter.ai/api/v1/models`), and `fastrouter/auto` fallback model, bringing its `$0` Starter Free Tier and `:free` models into the gateway (`internal/providers/providers.go`, `internal/providers/aliases.go`, `internal/providers/registry_aliases.go`, `internal/providers/registry_models.go`, `internal/providers/fastrouter_provider_test.go`).
- **Configurable per-provider member timeout in combo models.** `ProviderConfig` gains `ComboMemberTimeout time.Duration` and `providerCapacity` gains a `comboTimeoutMs` column so operators can configure a custom timeout from the dashboard's "Capacity limits" panel for any provider. `ChatHandler` implements `comboMemberTimeoutFor`, prioritizing the operator's configured policy in `providerCapacity`, then the provider's catalog declaration, and falling back to the 15s default across `/v1/chat/completions` and `/v1/messages`. Fluence configures a catalog default of 45s in `KnownProviders` to accommodate distributed peer routing and TTFT spikes (`internal/providers/providers.go`, `internal/db/schema.go`, `internal/db/provider_capacity.go`, `internal/handlers/dashboard/provider_capacity.go`, `internal/handlers/chat/combo.go`, `web/src/components/connections/ProviderCapacityPanel.svelte`).
- **Full-catalog `/v1/models` synchronization for Pi and Gentle Shell.** Whenever the gateway starts, the Pi CLI tool integration is applied, or custom models, disabled models, model aliases, combos, provider connections, or custom provider nodes change, NOX9GO now mirrors the active `/v1/models` catalog into both `~/.pi/agent/models.json` and `~/.gentle-shell/agent/models.json`. `SyncPiCatalog` updates the `nox9go` (or localhost gateway) provider block in place via `hujson`, preserving JSONC comments, `baseUrl`, `apiKey`, `modelOverrides`, and sibling providers while emitting both Pi schema fields (`id`, `name`, `reasoning`, `input`, `contextWindow`, `maxTokens`) and `/v1/models` metadata (`internal/clientconfig/pi_sync.go`, `internal/clientconfig/paths.go`, `internal/handlers/chat/models_list.go`, `internal/handlers/dashboard/*`).
- **Capacity limits extract generic `x-ratelimit-limit-*` headers and surface `rps`/`tpd` observations.** Providers returning generic `x-ratelimit-limit-requests` and `x-ratelimit-limit-tokens` headers without unit suffixes now populate `providerObservations` via `ClassifyHeaderObservations`, inferring `rps`, `rpm`, `rpd`, or `tpd` from `x-ratelimit-reset-*` headers alongside explicit `x-ratelimit-limit-tokens-day` / `tpd` headers (`internal/providers/observation.go`). `ProviderCapacityPanel.svelte` now surfaces `rps` and `tpd` observations with a `tok/day` label so operators can prefill those fields directly.
- **Capacity limits gain a "Requests / second" field.** Some providers publish a per-second request rate rather than a per-minute one (Mistral, for one), so the integrated-provider capacity editor can now declare it alongside `Requests / minute`. The value is stored in a new `providerCapacity.rps` column (added at boot by the existing additive column migration), travels through `GET`/`PUT /api/providers/{id}/capacity` with the same triangular-merge semantics as every other limit, and prefills from an upstream observation classified as `rps` — a per-second limit header or a "N requests per second" body. `0` means unlimited. It is declared policy only: the limiter still enforces rpm, so no existing throttling behaviour changes.
- **The Telegram channel can be paused without losing its token or allowlist.** Telegram allows one long poller per bot token, so a second client that needs the same bot (a desktop bridge, say) collided with the channel's poll loop and the only way to free the slot was to stop the gateway. `telegramChannel` gains a `paused` column (additive default `0`), the supervisor grows a `StatePaused` branch that stops the loop while the stored token and allowlist stay in place, and the dashboard exposes the switch as `PUT /api/channels/telegram/paused` plus an ON/OFF section in the Channels view with its Spanish literals (`internal/db/telegram_channel.go`, `internal/channels/telegram/supervisor.go`, `internal/handlers/dashboard/telegram_channel.go`, `web/src/views/ChannelsView.svelte`).

- **Fluence joins the API-key providers.** The paid OpenAI-compatible router (`https://api.fluence.cloud/v1/chat/completions`, `Authorization: Bearer`, key with the `inference` permission, prepaid credits or a monthly plan) is registered in `KnownProviders` with its published prefix `fluence` in `RegistryAliases` and live discovery at `https://api.fluence.cloud/v1/models`. Its catalogue is **scoped to the key**: `/v1/models` lists that key's routing profiles (`fluence/architect`, `fluence/coder`, `fluence/routines`, `fluence/cheapest`) plus the concrete models it may call, so `ProviderModels` ships no static row — inventing one would claim a model the upstream may refuse — and discovery is the only source of truth. Reasoning effort is a routing-profile setting (`effort_mode`/`efforts`), not a per-model wire shape, so no thinking format is declared; tool calls stay on, since Fluence serves them and converts legacy `functions`/`function_call` to tools. The dashboard gains the catalog card (`apikey` category, `hub` icon, the brand's square mark under `web/public/providers/fluence.svg`, notice translated in `es.json`). Verified against `https://inference.fluence.cloud/docs`: the same host also serves Anthropic Messages (`/v1/messages`, `x-api-key`) and Responses (`/v1/responses`), which this OpenAI-compatible entry does not use.
### Fixes
- **Zed completion streams unwrap the `{"event": ...}` envelope so Codex and Claude event translators receive native chunks.** Zed Cloud frames each JSONL stream line inside a wrapper object (`{"event": {<provider_event>}}` or `{"error": ...}`). Because downstream translators parse the payload as the raw event (`payload["type"]`), the outer wrapper caused event types such as `response.output_text.delta` to evaluate to empty and be discarded, producing 0 completion tokens and triggering HTTP 502 `upstream event stream carried no completion chunk` on non-streaming calls. `zedJSONLToSSE` now unwraps `event` (or maps `error` into a typed error event) before SSE framing (`internal/proxy/executor/zed_stream.go`, `internal/proxy/executor/zed_stream_test.go`).
- **Fluence routing profiles resolve to their upstream `fluence/<profile>` ID and expose live catalog import buttons.** Fluence publishes its routing profiles under the `fluence/` vendor prefix (`fluence/architect`, `fluence/coder`, `fluence/routines`, `fluence/cheapest`), while concrete models carry their own vendor prefix (`deepseek/...`). Because the gateway's provider prefix is also `fluence/` and the Add Custom Model dialog strips a leading `fluence/` on save, a request for `fluence/cheapest` reached upstream as `model: "cheapest"` and failed with HTTP 400 `auto_no_eligible_model` ("Disabled or removed from the catalog: cheapest"). `normalizeProviderModel` now restores the `fluence/` prefix for slashless Fluence model IDs, and `ProviderDetailView.svelte` adds `fluence` to `ModelsListURLs` so "Import from /models" and "Check Latest Models" render for the provider (`internal/handlers/chat/resolution.go`, `web/src/components/connections/ProviderDetailView.svelte`).
- **Providers whose artwork shipped but was never wired stop drawing the generic glyph.** `getIconPath` resolves artwork through the `ICON_FILES` lookup rather than guessing an extension, so a file under `web/public/providers` with no matching entry is invisible and the tile falls back to the initials badge. Two providers were in that state: `hetzner.svg` (since the Hetzner card landed) and the new Fluence mark. `web/src/components/connections/types.ts` now maps both, and `types.test.ts` — which already asserted that no catalog provider resolves to the generic glyph — is green again.
- **Combo Model Picker and Smart Combos stay in sync with active connections, custom models, and disabled models.** `resolveModelPickerGroups` no longer lists `noAuth` providers when any active connection exists or when the provider's connection rows are all inactive, includes custom models even when they define a display name (`name !== id`), matches custom models by either provider alias or provider ID, respects connection `providerSpecificData.enabledModels`, and strips `<alias>/` or `<providerId>/` prefixes when filtering `disabledModels`. `ModelPickerModal.svelte` invalidates its cached extras on custom/disabled model updates, `QuotaTrackerView.svelte` triggers a top-level connections refresh on toggle/edit/delete, and `smartComboCandidates` excludes hidden or unreachable custom-model providers as well as models whose canonical provider ID is disabled (`web/src/components/combos/pickerData.ts`, `web/src/components/combos/ModelPickerModal.svelte`, `web/src/components/QuotaTrackerView.svelte`, `web/src/App.svelte`, `internal/handlers/dashboard/combos_smart.go`).
- **The Vision/Audio Adapter now injects a model the gateway can actually dispatch, so a combo stops answering "cannot read images".** An enabled pool with no models of its own resolves to `defaultAdapterFallbackModel`, which was `oc/mimo-v2.6-flash-free` — an id that belongs to `ocg`/`opencode-go` and is absent from the `oc` catalog. The capability pattern match still reported vision, so the pool was consulted and the bogus candidate was prepended to the combo; dispatch failed, the request fell back to a text-only member, and `stripUnsupportedModalities` replaced the image with `[image omitted: model has no vision support]`. Because the factory settings enable the vision pool with an empty model list (`internal/db/settings.go`), this affected every default install. The fallback is now `oc/muse-spark-1.3-contributor-free`, present in the `oc` catalog and declared vision-capable, pinned by `TestDefaultAdapterFallbackModelIsDispatchableAndVisionCapable`, with the stored-pool rewrite covered by `TestGetSettings_UpgradesLegacyCapacityAdapterModel` (`internal/handlers/chat/capacity_adapter.go`, `internal/db/settings.go`).
- **The Vision Adapter card no longer reports a pool as ON when the gateway has none.** `parseCapacityAdapterSettings` defaulted an absent `capacityAdapter` entry to enabled, while the backend treats a missing entry as disabled (`normalizeCapEntry` returns the zero value), so a card that had never been saved showed a working adapter that injected nothing. An absent pool now reads OFF; a stored entry keeps the backend default. `saveCapacityAdapter` also restores the previous state when the settings PATCH fails instead of leaving the toggle painted ON over a write that never landed (`web/src/components/combos/types.ts`, `web/src/components/combos/CombosView.svelte`).
- **Model/combo/vision/audio pickers no longer list providers the operator removed or deactivated.** Upstream 9router keeps every connection — active or not — selectable in `ModelSelectModal`, so a provider you had deactivated (or a compatible node you deleted, leaving orphaned custom models in the DB) kept offering its models in the picker. `resolveModelPickerGroups` now only credits connections with `isActive != 0` and requires an active connection row for custom provider nodes, deliberately diverging from upstream (NOX9GO behavior request; `web/src/components/combos/pickerData.ts`).
- **Telegram channel skips duplicate getMe on bot init.** `go-telegram/bot` already calls `getMe` during `New` unless `WithSkipGetMe` is set; the channel uses one explicit `GetMe` after create so restarts do not double-hit Telegram rate limits (`poll.go`).
- **Opening a Telegram panel deletes the one it replaces, and transient bot errors stay off the channel status.** Every `/panel` (and every inline button that opens one) stacked another message, so the thread accumulated live keyboards that all answered the same taps; `openPanel` now deletes the previous panel message before sending the new one (`modes.go`, `poll.go`). Failures the bot SDK retries on its own are no longer forwarded to `setError`, so a transient local abort does not surface as the channel's `Last error`.
- **Telegram Bot API bypasses ambient HTTP_PROXY.** `getMe`, long-poll `getUpdates`, and Telegram file downloads dial `api.telegram.org` directly instead of inheriting `HTTP_PROXY` from the gateway environment, which previously surfaced as `error sending request for url` on Windows (`poll_transport.go`, `image.go`).
- **Gentle Shell desktop feed is not filtered by `HERDR_AGENT_EXCLUDE_CWD`.** The Herdr order exclude still applies to `herdr agent` attachment, but passive Telegram→Herdr blocker discovery must read desktop session snapshots whose `identity.cwd` is the gateway checkout (`gentle_desktop_feed.go`).
- **Bump `github.com/gorilla/websocket` for GO-2026-6278.** `govulncheck` reported a weak PRNG in the WebSocket mask key on v1.5.3; direct require moves to the patched pseudo-version so CDP login and Gemini Live STT paths stay clean.
- **Telegram `getUpdates` transport noise no longer fills `Last error`.** The bot library's errors handler forwarded every failed long poll to `setError`, so intermittent local TCP aborts (Windows `WSAECONNABORTED` / `wsarecv` while the socket waited ~50s for updates) showed up on the dashboard even though the poll loop stayed `running` and the SDK retried. Transient poll transport failures are filtered, the long-poll window is 45s instead of ~59s, and the HTTP client timeout is sized for that window so idle sockets recycle before firewalls or AV often cut them (`poll_transport.go`, `poll.go`).
- **Telegram Herdr orders tolerate Herdr CLI stderr under `Stop`.** Herdr prints JSON errors on stderr (`agent_not_idle` on read, `agent_blocked` on prompt); PowerShell treated those as terminating errors so orders reported `order_failed` instead of polling or exiting as a blocker. The runner now wraps Herdr calls in `Invoke-HerdrArgv`, falls back to `--source visible` while Pi is working, and maps `agent_blocked` on prompt to exit `2` (`scripts/run-telegram-order-herdr.ps1`).
- **Telegram agent mode: shorter Herdr replies and remote answers.** Order output filters Pi panel noise (TPS, status footers, tool hints) and caps the delta shown in chat. A Herdr `blocker` moves the task to **Herdr espera tu respuesta**; the next Telegram message is relayed into the panel (`herdr pane send-text` + Enter) instead of queueing a new prompt. Stale ↑↓ menus are dismissed with Esc before the next order (`NOX9GO_HERDR_RELAY=0` disables relay).
- **HERDR_AGENT_TARGET=focused follows the active Herdr Pi pane.** Set `focused` (or leave the runner default) so Telegram orders and blocker buttons attach to whichever gentle-shell agent has `focused:true` in `herdr agent list`, instead of a fixed name when switching projects (Pepe, Maria, …).
- **Telegram Herdr passive blocker watcher.** When `NOX9GO_HERDR_WATCH` is on (default with the Herdr order runner), the bot polls the focused Pi pane every few seconds and sends the same inline blocker buttons if a menu appears while you work locally in gentle-shell — not only after a Telegram order exits `2` (`internal/channels/telegram/herdr_watcher.go`).
- **Telegram Herdr attaches to gentle-shell, not a duplicate nox pane.** Focused resolution prefers agent `shell` over legacy `nox`, optional `HERDR_AGENT_WORK_CWD` / `HERDR_AGENT_EXCLUDE_CWD`, `ask_user_choice` transcript parsing, and watcher errors on the channel status. `start-herdr-workspace.ps1` no longer registers a separate nox agent.
- **Telegram Herdr pane fallback when `agent list` is empty.** Gentle-shell can run with a focused pane but no registered agent row; orders, watcher, and blocker keys use `herdr pane read` / `pane send-keys` on that pane instead of failing with no focused agent.
- **Telegram Herdr auto-registers `shell` on the focused Pi pane.** Pane-only reads usually see only the outer PowerShell prompt, so the runner and passive watcher call `herdr agent start shell --kind pi` once when `agent list` is empty (`HERDR_BOOTSTRAP_AGENT=0` to disable).
- **Telegram Herdr blocker buttons answer via Gentle Shell desktop inbox.** `ask_user_choice` prompts detected from the desktop feed are answered with `answer_question` + `via: session` under `~/.gentle-shell/agent/desktop/inbox/<session>/`, not only `herdr agent send-keys` (`gentle_desktop_action.go`).
- **Telegram Herdr passive watcher reads Gentle Shell desktop feed.** `ask_user_choice` often leaves `agent_status` at `idle` and `screen_detection_skipped:true`; the real question lives in `~/.gentle-shell/agent/desktop/sessions/*.json` (`pendingQuestion`, `activity.state=blocked`), so the passive watcher scans that feed before pane scrape (`gentle_desktop_feed.go`).
- **Telegram Herdr passive watcher parses Pi `->` cursor menus.** Gentle Pi marks the selected row with ASCII `->`, which the blocker parser ignored, so Herdr→Telegram stayed silent while ChatBot→Herdr worked; free-text prompts (`Type your answer`) now notify without buttons.
- **Telegram Herdr blocker buttons: cleaner parse and layout.** Cursor menus only accept arrow- or indented rows; duplicate Confirmar/Cancelar chrome drops when real options exist; one button per row for short menus; feed shows the dialog question instead of stacking title + panel dump.
- **Telegram Herdr orders submit via pane send-text + Enter.** `herdr agent prompt` mis-parsed prompt text as CLI flags (e.g. `con` from `confirm`); orders now type into the agent pane like the operator (`scripts/run-telegram-order-herdr.ps1`).
- **Telegram Herdr order output trims Pi footers and honours "responde solo:".** TPS/Panel/waiting-for-input lines are dropped; echo-only orders return the expected line only (`scripts/run-telegram-order-herdr.ps1`).
- **Telegram Herdr blocker buttons and Pi extension installer.** `blocker` feed events parse the live pane (`herdr agent read`) into inline buttons that call `herdr agent send-keys` (cursor/numbered/permission heuristics adapted from [herdr-telegram-bridge](https://github.com/spancerxing/herdr-telegram-bridge), MIT). `scripts/install-herdr-pi-bridge-extension.ps1` installs the bridge's Pi `herdr:blocked` emitter alongside `herdr integration install pi`.

- **The Pi/Gentle Shell catalog sync is deterministic and no longer rewrites `models.json` on every dashboard write.** `buildModelsListForMode`, `appendNoAuthCatalogModels`, `appendConnectionModels` and `appendLooseCustomModels` walked Go maps directly, so the published `/v1/models` order changed on every call. That was invisible in a single HTTP response, but `SyncPiCatalog` persists the catalog to disk: each model, combo, connection or provider-node write rewrote a 1.7 MB `models.json` with the same models shuffled and could never report `unchanged`. Provider aliases, alias targets and custom-model provider keys are now sorted before emission, so the same catalog serializes byte for byte and a no-op sync stays a no-op (`internal/handlers/chat/models_list.go`).

### Features
- **Poolside leaves the provider grid.** Its self-serve free inference was shut down on 2026-10-31, so the provider no longer occupies a slot: `Hidden: true` on the backend catalog (`internal/providers/providers.go`) and `"hidden": true` on the frontend list (`web/src/lib/providers.ts`), which `ProvidersOverviewGrid.svelte` filters on. Hidden is not deletion — the entry keeps its `BaseURL` and its `ps` alias, so a stored connection still resolves and reviving the upstream is one flag.
- **The sidebar shows whether the Telegram bot is alive.** `GET /api/status` now reports the poll loop's state (`telegram.state`) through the shared runtime, and an unreported runtime answers `disabled`, so the badge never claims a chatbot it cannot prove is running. `ServiceStatus` renders it as a third `Bot` badge — a dot when the sidebar is collapsed — fed by the same 15 s poll: green only while the loop reports `running`, idle otherwise.
- **Herdr order runner for live Pi panes.** `scripts/run-telegram-order-herdr.ps1` submits `herdr agent prompt` to `HERDR_AGENT_TARGET`; blocked agents emit `blocker` feed events without closing the task, done/failed use the existing spool outcomes. Terminal-output fallback covers Pi panes Herdr leaves on `idle`; `HERDR_AGENT_WAIT_MS` caps `agent wait` separately from the long poll timeout; invalid `DEV_REPO_ROOT` no longer aborts `Set-Location`.
- **Telegram agent orders can execute on this machine.** With `DEV_ORDER_RUNNER` set (e.g. `scripts/run-telegram-order.ps1`), the channel drains `dev-inbox.jsonl` on a timer, runs each `order` locally, and appends `order_done` / `order_failed` to the feed so the panel closes without hand-writing spool lines. `DEV_AGENT_CMD` (or `codex` / `agent` on PATH) defines how the script runs the instruction.
- **The inline panel stays reachable.** `/panel` is pinned when opened, `📋 Menú` refreshes the existing panel instead of stacking another message, and hub dock refreshes stop flooding the thread with repeated legend text.
- **A running Telegram task closes when the development session reports back.** The agent panel stayed on `Ejecutando` after the session finished because nothing moved the row in `telegramAgentTask` to `done`. The feed drain now maps `order_done` events (and the legacy `task`/`info` titles that say the order completed) to `Completada`, sends `Tarea [xxxx] completada.` to the chat, and redraws the panel; `order_failed` and matching failure titles land in `Fallida` with the reason. Manual spool lines should set `task_id` to the Telegram correlation id and put the **agent answer** in `detail` (empty `detail` still applies to whatever task is running when only the title matches).
- **Telegram UX pack (8 proposals).** (1) Hub dock: three buttons only — Menú, Modo, Teclado — with full navigation on the inline `/panel`. (2) Agent inline panel drops the heavy nav rows while a task is pending or running; they return when idle. (3) `Último evento` on the panel from the drained feed. (4) Rotating input placeholders per mode. (5) `correlationId` on agent tasks and `task_id` on spool events. (6) **Compacto** auto-hides the dock when entering agent mode. (7) Agent images get a `SendPhoto` confirmation with the saved path. (8) **Feed** cycles Todo → Solo tareas → Silenciado; task outcomes still reconcile when silenced. `scripts/dev-spool-notify.ps1` accepts `-TaskId`.
- **The dock refresh survives Telegram's empty-text validation.** The keyboard refresher carried U+200B (zero-width space) as its text, and the Bot API started rejecting that payload with `Bad Request: text must be non-empty` — U+2800 (Braille blank) after it proved the API now rejects every invisible-only text. The refresh travels visibly as a one-line `⌨️` now, and callback presses no longer re-send the dock on every tap: Telegram persists the reply keyboard between messages, so a refresh goes out only when the keyboard was never drawn by this process or the press actually changed it (`internal/channels/telegram/keyboard.go`, `modes.go`).
- **Order scripts run on any platform.** The inbox-order runner spawned `powershell` unconditionally, so on a Linux host every order aborted with `executable file not found in $PATH` — the failure that took down the Backend and race-shard CI jobs. `orderRunnerCommand` now picks the interpreter from `runtime.GOOS`: PowerShell with the same flags on Windows, `/bin/sh` elsewhere. `DEV_ORDER_RUNNER` keeps naming whatever script the operator wants, and the exit-2 blocker contract is unchanged; the runner tests now write the script each host can execute and the `/bin/sh` branch was verified on Ubuntu (exit 0 → done, exit 2 → blocked) (`internal/channels/telegram/inbox_runner.go`).
- **Agent UI deduplication: dock vs inline.** With the dock visible, the agent inline panel drops `Estado / Paso` and `Autonomía` (the dock carries `📋 Tarea actual` and `⚙️ Autonomía`); those return when the keyboard is hidden. Agent dock no longer shows `Cancelar turno` — that action belongs to chat mode only — so a tap cannot be mistaken for cancelling a supervised task. Terminal task states get `Refrescar` only, not the auto-approve row.

### Tooling
- **Patch coverage can be predicted locally, before the push.** Codecov's `patch` status compares the lines a commit touches against the profile CI uploads, and it does that without asking whether a touched line is executable: the whitespace-only commit `374447ab` scored 50% on two "changed lines" and failed a 67.9% target, while its target drifted from 67.70% to 67.90% because it sits on `auto`. Both facts are only visible after the push, which is the wrong time to learn them. `bun scripts/diff-coverage.mjs` answers the same question against Go's own profile: it runs `go test -coverprofile` for the packages a diff touches, intersects the changed line numbers with the cover blocks, and — deliberately — does not count a changed line that no block contains, because struct alignment, comments, imports and a trailing newline carry no coverage either way. On the commit that failed CI it reports 50.00% over 12 instrumented lines, matching Codecov, and it exits non-zero so a hook or a human can act on it. `--worktree` includes uncommitted changes, `--base` accepts any git range. Documented in `AGENTS.md` §8.
- **A `bun` script does not run in a clean environment: bun loads the project's `.env` first.** Every key in it — `ROUTER_MASTER_KEY`, `CLOUDFLARE_ACCOUNT_ID`, the OAuth client secrets, `DEV_*` — lands in `process.env` and is inherited by anything the script spawns, so `bun` + `execFileSync("go", ["test", …])` runs the suite with credentials a plain `go test` never sees. That is a leak, and it also changes results: with `CLOUDFLARE_ACCOUNT_ID` present, `TestHandleValidateProvider_CloudflareRequiresAccountID` fails because the handler finds an account id the test asserts is missing — a local red that CI never reports. The new script builds its own whitelisted environment for the child process, and the trap is recorded in `AGENTS.md` §0.2 so the next bun script does not inherit it too.
- **Two `make` targets that cannot run on a machine whose paths contain spaces are documented instead of silently failing.** `cross` recurses with an unquoted `$(MAKE) -j …`, so `C:/Program Files (x86)/GnuWin32/bin/make` is split by the shell; `vet-svelte` starts with `bun install --frozen-lockfile`, and `web/bun.lock` is `lockfileVersion: 2`, so an older bun refuses the install before checking anything. ### Telegram bot UX (2026-11-22)
- **The chat and the agent have their own modes, and the bot says which one is listening.** Free text used to have one meaning, so the operator could not keep a conversation and hand work to the development session from the same chat. `/panel` (and the mode buttons) switch between them: chat mode forwards the text as conversation through the active session, agent mode records it as a task awaiting the operator's own approval. The mode is stored per chat, shown in the panel header, and readable from the dashboard (`GET`/`PUT /api/channels/telegram`).
- **The panel shows the task, not just a hint.** While a task is under way the agent panel carries `Pendiente: <instruction>` instead of a generic hint, so an operator returning to the phone sees what he approved rather than an empty welcome.
- **Cancelling confirms only after the turn is actually dead.** `cmdCancel` used to answer before the in-flight turn finished unwinding, so a follow-up message could race the dying turn. The turn now exposes a done channel and the confirmation waits (2 s timeout) for it.
- **The bot registers its command menu and `/start` teaches it.** `SetMyCommands` runs at poll start, so Telegram Web and mobile show the ☰ menu; `/start` sends the help text plus the panel, `/help` stays a pure query, and the menu commands are pinned by a test that cross-checks each one against the help text.
- **Each mode owns a persistent reply-keyboard dock.** Chat: new session, models, sessions, channel status, cancel, close, switch to agent. Agent: current task, dev status, ODD feature picker, channel status, cancel, sessions, switch to chat. Every label resolves through the existing command paths, so the dock is a second entry point and never a second behaviour, and the turn acknowledgement carries the whole dock — the lone `Cancelar` row it shipped before silently wiped the dock on every chat turn.
- **Model, session and ODD-feature pickers open as inline panels.** They reuse the data the typed commands read, edit in place instead of flooding the chat, and truncate callback payloads inside Telegram's 64-byte budget with a prefix map-back that refuses ambiguous prefixes.
- **A session can be retaken from the picker.** `ResumeTelegramSession` is one transaction that archives the chat's other open session and clears the tapped one's archive stamp, so "ver sesiones" is a control rather than a history view.
- **Approving a task executes it, instead of only flipping a status.** Approve, auto-approve and `/pi` share one delivery path (`submitOrder` → the development session's inbox), and the status follows the real result: `running` is written only after the order was accepted, and a rejected submission stores the cause and says so on the panel. Approving used to change a database column and call that execution — the executor existed all along in `/pi`, nothing connected the button to it.
- **A fault no longer paints the channel red forever.** `setError` overwrote the whole status with `error`, so one expired long-poll left the dashboard wrong until a restart nobody asked for: the loop was alive, but nothing could clear the state. The fault is reported as `lastError` and only a loop that is not running can report `error`, which is the start-up failure where there is genuinely no channel.
- **A task left running by a previous process is closed on start.** Its order may still be drained by the development session, but the restarted gateway cannot know that, and a panel that says `Ejecutando` forever is worse than one that admits the order was lost. The task is closed as failed with the reason, and the 📋 Tarea actual button reports state, instruction and reason without submitting anything — it replaced ⚡ Orden a Pi, which duplicated the free-text path with different approval semantics and confused exactly the operator it was meant to help.

### Telegram channel

### Development status
- **The operator can see where a feature stands, from the phone or the dashboard.** `/estado` reports the branch, the last commit and its age, the recent history, the uncommitted files and — when an ODD document is named — its task progress and next pending task. `/estado <feature>` follows a different document for one call; with no argument it follows `DEV_FEATURE`. Implemented once in `internal/devstatus` and rendered by both consumers, so the bot and the dashboard cannot drift: the bot prints it as message text, `GET /api/dev/status` returns the same string plus structured fields for the panel. A monotonic commit count of "tasks done" would have been easy to write and wrong; completion is read from each task's commit cell, with the em-dash placeholder treated as pending rather than as a hash — otherwise a freshly written document would report 100%. The direction is one-way by design — nothing reads a chat message back as an instruction, so a mistaken or hostile message can at most ask for a status report, never change what the code does. Delivery is fail-closed: an empty allowlist drops the event even when one is waiting, so a config change mid-flight cannot leak a report. ### Telegram channel

- **The gateway can now be driven from Telegram, as a channel separate from the dashboard.** A bot answers the operator's own chat and each free-text message becomes a turn through this instance's `/v1/chat/completions`, so the bot is a client of the gateway it runs inside, not a second implementation of it. ### Provider capacity

- **`Capacity limits` gains a `Tokens / day` budget, the token counterpart of the existing daily request budget.** Most free tiers are published as a daily token allowance ("150K tokens/day, resets at 00:00 UTC"), and the only token axis the gateway had was `tokenQuota` — a lifetime ceiling measured from a reset marker — so an operator enforcing a free tier had no way to express "this refills tomorrow". `dailyTokens` is a new axis modelled directly on `dailyRequests` (`internal/db/schema.go`, `internal/middleware/ratelimit.go`): the same fixed UTC-day window, the same midnight-UTC refill, `0` meaning unlimited, negative values refused at the storage boundary. It is additive on both `providerCapacity` and `providerNodes`, so the integrated-capacity editor and the OpenAI/Anthropic-compatible node editor carry it identically, and the PUT keeps its tri-state merge (omitted keeps, `0` clears, a number sets). `tokenQuota` keeps its lifetime meaning unchanged; a provider may carry both. The two axes differ in one way that matters: a request budget can be charged atomically before dispatch, while a streaming turn's token cost is unknown until it ends, so the prompt estimate is reserved at admission and `ProviderSlot.Settle` charges only the difference once the real total arrives — an attempt that never produces a usage reading has its whole charge refunded by `Release`. A refusal on this axis is congestion (`429`-able, axis `tpd`), never a node-state `403`, so the request falls through to the next candidate. The field renders in both editors with the hint `A fixed daily budget. It resets at 00:00 UTC, not one minute after the first request.` and is translated in `es.json`. Covered by eight new limiter tests (`ratelimit_provider_daily_tokens_test.go`) pinning the refusal, the UTC-boundary refill, independence from the lifetime quota, the congestion classification, the settle-only-the-difference rule and the full refund, plus one test pinning that the existing request-per-day budget is unchanged by the new axis, and the capacity round-trip/negative-rejection cases extended in `internal/db`. `go test ./...` green across 61 packages, `go vet` clean, SPA rebuilt (2739 KB → 582 KB brotli), svelte-check ratchet unchanged at its 71-error baseline.

- **A provider observation with invalid UTF-8 no longer breaks the capacity endpoint.** SQLite stores bytes, not text, so a `providerObservations.evidence` value cut mid-rune by an earlier writer read back without error and only failed later, when `encoding/json/v2` refused it. Five such rows existed in the live database (`bazaarlink` 2, `codebuddy-intl` 3, all dated 2026-11-06/07), each carrying a Chinese free-tier message whose last rune was truncated: `GET /api/providers/{id}/capacity` answered `500` for those providers, and after a restart answered `200` with the body truncated at the bad byte and the error object concatenated after it — worse, because a caller that does not parse the body sees success. `repairUTF8` (`internal/db/provider_capacity.go`) now runs on the read path in `ListProviderObservations`: it walks forward rune by rune and returns the longest valid prefix, so the observation's signal, value and sample count survive and the operator still reads why the provider refused. A clean row comes back byte-identical. The five stored rows were repaired in place (recut to the last valid byte, nothing deleted) after a database backup, and a deliberately corrupted row was used to prove the deployed binary serves it repaired. Covered by `provider_capacity_utf8_test.go` (database round-trip with a lone lead byte, a clean row left untouched, and seven `repairUTF8` shapes), all failing before the helper existed.

- **Qoder presents one stable device per account, ending self-inflicted queue timeouts.** `buildQoderCosyHeaders` generated a fresh random `Cosy-Machineid` on every request when the connection stored none — which is every PAT connection. - **Gemini's OpenAI-compatible endpoint no longer receives an unsupported `store` field.** `executor.ForwardOpenAI` passed the client body through byte for byte unless the provider was `groq` or `cloudflare-ai`, and Gemini answers `400 INVALID_ARGUMENT` — `Invalid JSON payload received. - **Kiro tool-call IDs use UUIDs.** `OpenAIToKiro` maps non-UUID tool-call IDs to per-request UUIDs and reuses that mapping for matching tool results; valid UUIDs remain unchanged. Added `github`/`gh` to `strictReasoningMessageProviders` to strip unsupported reasoning fields. - **Cloudflare AI schema sanitization and message content flattening.** `SanitizeOpenAITools` now cleans `response_format.json_schema.schema` via `cleanResponseFormatSchema`, recursively stripping unsupported grammar keys (`propertyNames`, `$schema`, `$comment`) while preserving `additionalProperties` for strict JSON schema mode. Chat completions for `cloudflare-ai` flatten multipart text content arrays to avoid upstream schema validation errors.
- **Combo non-retryable 400 loop termination.** `handleComboFallback` and `handleMessagesComboFallback` now immediately abort retry loops on non-retryable HTTP 400s rather than repeating 10 identical attempts on the same connection. Probe requests now honor `maxConsecutive429PerTurn` to prevent hammering multiple accounts when a provider rate-limits.
- **Groq `max_tokens` over the model cap no longer fails the request.** Groq rejects a `max_tokens` above the model's output limit with a 400 that names the limit ("`max_tokens` must be less than or equal to `16384`"). The gateway forwarded the body verbatim, so every request asking for more — including one whose value came from a client-config placeholder — died at the first attempt. `executor.ForwardOpenAI` now parses the cap the upstream states (`translator.MaxTokensLimitFromError`), clamps `max_tokens`/`max_completion_tokens` to it (`translator.ClampMaxTokens`) and retries once; if the retry fails, its error is returned instead of the stale pre-clamp 400. The upstream's own number is the source of truth: the model catalog describes the model, not each gateway's per-model cap. Any other 400 surfaces unchanged.
- **The Pi client config no longer invents a 64000 output cap.** `internal/clientconfig/pi.go` wrote `contextWindow: 200000, maxTokens: 64000` for every model it registered, which is what made a Pi client request a `max_tokens` Groq rejects. It now derives both numbers from the capability catalog (`providers.GetCapabilitiesDetailForModel`) and omits a field the catalog cannot answer instead of guessing.
- **Gemini's OpenAI-compatible endpoint gets its thought signature backfilled.** Gemini 3 refuses a current-turn `functionCall` with no `thought_signature` (400 INVALID_ARGUMENT "Function call is missing a thought_signature in functionCall parts"). Only the native/Antigravity path ran that fixup, so the `gemini` provider — which talks to `generativelanguage.googleapis.com/v1beta/openai/chat/completions` — reached upstream unsigned whenever a client dropped the field or a combo rebuilt the history. `translator.BackfillOpenAIToolCallSignatures` now injects `extra_content.google.thought_signature` into assistant `tool_calls` that lack one, using the cached signature for that id (session-scoped) or `DefaultThinkingSignature`; `translator.HarvestOpenAIToolCallSignatures` stores the signatures Gemini returns so later turns replay the real one. Applied only for `gemini-openai` providers.
- **A run of consecutive 429s now parks the provider+model pair, not just one walk.** `maxConsecutive429PerTurn` already stopped the failover walk after five 429s across different credentials, but it bounded one turn and nothing else: the next turn dialled the accounts the first one never reached and earned the same answer. A free-tier pool of many keys was therefore spent in a couple of minutes — a combo member like `mistral/mistral-medium-3-5` burned 72 of 78 connections into cooldown while the operator was not even using that provider, and the dashboard read "rate limited" on the whole pool. A single 429 must still leave the pair routable (one 429 names a per-account or per-IP limit the operator's other keys may serve, which is why `providerModelQuotaMarkers` excludes "rate limit"), but five different credentials answering 429 for the same model inside one turn is a fact about the pair. `ChatHandler.recordProviderModelRunLockout` (`internal/handlers/chat/provider_model_lock.go`) parks it through `LockProviderModel` with reason `rate_limit_cascade`, called from `handleAccountFallback` and from both combo paths (`handleComboFallback`, `handleMessagesComboFallback`). The window is the failing attempt's own cooldown — an announced `Retry-After` honoured exactly — floored at 30s so a two-second classifier base cannot put the pair back inside the burst that answered all five. The existing pair check then skips the model whole on the next request, and any account that serves it again clears the lock. Covered by `TestHandleAccountFallback_Consecutive429ParksProviderModel`, which asserts the pair is parked and that the follow-up request makes zero upstream calls.

## [1.0.3] - 2026-10-30

The pre-publication audit (`docs/auditoriaUnificada.md`, 35 items) is closed except for two that need the repository owner to act on GitHub: the repository topics and the deletion of a local branch holding leaked OAuth secrets.

### Security

- **Admin routes no longer accept a client API key.** `RequireDashboardAuth` accepted any active engine key, so consuming the gateway was the same as administering it — create and delete connections, mint and revoke keys, change settings, rotate the vault. Only the dashboard session cookie and the local CLI token open the admin group now; a client key gets `401`. The rest of that gate (the local CLI token, the re-typed password header on the export route) is unchanged. *The audit's item 1.1.*
- **The proxy no longer retries a failed TLS verification with verification off.** A certificate that did not validate was retried with `InsecureSkipVerify`, which is exactly the request an interception proxy wants: it carries provider tokens, API keys and the conversation. The retry is gone. An operator behind a corporate MITM appliance sets `ALLOW_INSECURE_TLS=true` to opt in, and `.env.example` documents installing the appliance's CA as the preferred fix instead. *Item 1.2. The code also read `STRICT_SSL` with `os.Getenv`; the new variable is documented next to the loader so a value in `.env` is known to reach it.*
- **`INITIAL_PASSWORD` is honoured again.** `config` parsed it into `Config.InitialPassword` and nothing read the field, so an operator who set it still got a generated password — and the startup notice advised setting a variable that did nothing. It is now the password when set (and is not forced to be replaced, because the operator chose it); blank counts as unset. *Found by the end-to-end job, which boots the gateway with it and logs in.*
- **The dashboard password is generated at first start, printed once, and must be replaced.** A fresh install accepted `123456` — the value every 9router install shares. Hiding it from the README would not have helped, so the behaviour changed: the first start writes a random 24-character password, prints it in a block that says it is shown once, and the login with it answers `403 mustChangePassword` until a new one arrives in the same request. A stored hash of the old default counts as unset, so an upgraded install is migrated the same way. The "must change" state is an explicit `passwordGenerated` marker in settings, not a guess from the hash: a bcrypt hash carries no information about where the password came from, and the first version of this returned `200` for the generated password instead of `403`. The startup notice prints the port the gateway actually bound, not a literal `20130`. *Item 1.3.*
- **`.env.example` no longer ships working defaults.** `JWT_SECRET=change-me-to-a-long-random-secret` and `INITIAL_PASSWORD=change-me` were both usable as-is, and the `change-me` password also disabled the protection it looked like it provided, because that guard only checked for an empty value. Both are commented out with an explanation, and `DATA_DIR` is documented as per-platform instead of `/var/lib/nox9go`. *Item 1.3.*
- **The updater can no longer install a binary for another platform.** `version.json` published one `downloadUrl` — the Windows executable — and the updater took it on every platform when no platform-specific entry existed, so a Linux or macOS install could download and swap in a binary it cannot run; the checksum did not help, it only proved the bytes were the published ones. The manifest names a URL and a `sha256` per platform, an unlisted platform is refused rather than falling back to the first non-checksum asset, and the downloaded file is parsed (PE, Mach-O or ELF) to confirm it is an executable for this OS and, where the header records it, this architecture before it replaces the running binary. `scripts/gen-version-manifest.mjs` writes the manifest and `--check` validates it without touching it. *Item 1.5.*
- **The personal environment is out of `AGENTS.md`.** Absolute paths, the author's user name, the initial password, Engram identifiers and `.atl` references described one machine, not the project. `.rtk/` and `.atl/` are ignored and untracked. *Item 1.6.*
- **Secret scanning runs in CI.** `gitleaks` over the full history on every push: a secret removed from `HEAD` is still leaked in the commits behind it. *Item 5.*
- **`data`, `web/dist`, SQLite sidecars and every `.env` variant are ignored.** `.env.local` and `*.db` were committed by `git add -A` before; the resolved data directory holds every provider token and the WAL holds committed pages. *Item 22.*

### Documentation and repository

- **`SECURITY.md`**: how to report privately, what to include, how a report is handled, what is in and out of scope, and what to do when a credential leaks — revoke first, because rotating it in the repository does not remove it from the history that was pushed.
- **`CONTRIBUTING.md`**: requirements, the build and test commands that actually exist, the convention that a divergence from upstream is labelled with why, and the changelog rule.
- **`THIRD_PARTY_NOTICES.md`**: the 9Router and 9router-go attributions, the provider catalogue source, the Go and frontend dependencies, and the provider logos that are trademarks and not covered by MIT.
- **`LICENSE` is recognised as MIT again.** The attribution paragraph sat inside the permission text, so GitHub read the file as `NOASSERTION`/"Other". The licence and every copyright notice are unchanged; the paragraph moved above the permission paragraph.
- **CI.** A workflow on push and pull request: frontend install with the frozen lockfile, the svelte-check ratchet, lint and build; `go vet`, `go test ./...` and a clean build against that bundle; the race detector; `gitleaks`; `govulncheck`; the update-manifest check; and the end-to-end suite in its own job. ## [1.0.2] - 2026-10-28

Provider probes that tell a network block from a bad key, OpenCode in the CLI tools screen, and a dashboard that shows this project's own change log.

### CLI tools

- **OpenCode is a CLI tool the dashboard can drive.** A new `clientconfig` registry gives every CLI client a shared patch/paths abstraction, so a tool is driven by one code path instead of one path per client. The OpenCode adapter reads and writes `opencode.json`/`opencode.jsonc`, tolerates comment-style JSONC, and **merges** the provider block instead of overwriting the operator's own agents and permission rules. The new backend endpoints let the web UI inspect and rewrite that config, and the CLI tools screen grows an OpenCode card that shows the detected config path and applies the NOX9GO provider without losing the existing ones. *Tests cover the JSONC parsing and the patch merge.*

### Provider probes and catalogues

- **A network block is no longer reported as a bad key.** Groq answered every provider test with `403 Access denied. Please check your network settings.` and the dashboard called it "Invalid API key or base URL", so the operator went hunting for a credential problem that did not exist — the key was never read, and the same 403 comes back for a bogus bearer, for the bare host and for every model at once, with `Server: cloudflare` in the headers. The status code cannot tell the two apart, so the body decides: `looksEdgeBlocked` matches an infrastructure phrase ("check your network settings", Cloudflare's 1020/1010, "just a moment", "attention required") but yields to any phrase that names the credential, so a genuine key rejection is never relabelled as a network problem. The blocked outcome says the key was not evaluated, points at the egress, and logs the body at WARN so the log stops calling it a rejected credential. Wired into `validateGeneric` on both the `/models` probe and the chat fallback, and into `probeCompatibleConnection` on both the OpenAI and Anthropic-compatible branches.
- **A known provider with no static catalogue answers 200, not 404.** `GET /api/models/caps?provider=zed` answered 404 on every dashboard load. The route and the handler were fine; the handler's own empty-map branch collapsed two different situations into one status — "this provider has no static models" and "this provider does not exist". Zed serves its catalogue live, so it has no static list and always landed in that branch, while compatible nodes and provider nodes were already answered with an empty 200. The registry is consulted first now: a known provider gets `200 {caps: {}}`, and the 404 is kept for the only case where the status is true — an id the registry does not know and no node backs.
- **A Zed turn that folds to nothing says what the stream carried.** "upstream event stream carried no completion chunk" named a symptom and nothing else, and that one sentence was reaching the log for three unrelated faults: an empty stream, a stream whose events never parsed as JSON objects, and a JSON stream of event types the fold does not model. Each wants a different fix, and the message could not tell them apart. The fold now counts the events it discards and, when nothing was recognised at all, logs the raw size, that count and the first 500 bytes; discarded events are logged at DEBUG with their own head, so a stream that arrives in an unexpected shape is visible instead of silently absent. `zedHead` renders a body for a log line: control bytes and newlines are escaped so a multi-line SSE frame cannot break the log and a binary or gzip body cannot wreck it, and a truncated sample is marked so it is not read as a complete one.

### Routing and quota

- **A malformed request stops the combo instead of burning it.** A 400/422 whose body marks the request itself as malformed or unsupported (bad tool-call payload, unsupported modality, out-of-range `max_tokens`, `invalid_request_error`) was falling through the combo loop's generic `continue`, so every remaining combo member was tried against the same body and rejected in turn — one connection per member, until the pool was saturated. `IsRequestInvalidError` (a sibling of `IsModelFitError`: fit-error covers "too big", request-invalid covers "wrong shape") breaks the turn in both combo loops, OpenAI and Claude. The account is not at fault, so `comboLockRetryable` is skipped, same as fit-error; the single-provider fallback path already filtered through `RetryableStatusCodes` and needed no change.
- **CodeBuddy honours the exact reset instant the 429 names.** A spent model quota comes back as HTTP 429 with an absolute reset instant in the body ("usage exceeds frequency limit... reset at 2026-10-28 11:29:25 UTC+8"). Two things dropped that instant: the executor replaced the body with a generic message, and the cooldown path clamped every reset hint to 2h. The model was therefore retried while the quota was still spent, which is what turns a frequency limit into an account restriction. The executor now keeps the upstream body, and `retryableCooldownSec` takes the provider so the CodeBuddy branch can honour that instant exactly. The lock is per connection and model, because a CodeBuddy quota belongs to the OAuth account: the provider+model pair lockout stays opt-in and off, so healthy keys keep serving.
- **CodeBuddy parks restricted accounts, paces requests and refreshes tokens.** An account answering code `11140` is cooled down for 12h instead of 2m, requests are spaced 1.5s per credential, and OAuth refreshers are registered for `codebuddy-cn` and `codebuddy-intl`. *Ported from `decolua/9router` `tokenRefresh/providers.js`.*

### Dashboard

- **The change log shows this project's notes.** The "Change Log" entry in the account menu opened a modal fed by `/api/changelog`, a route mounted with the engine routes behind `middleware.RequireApiKey` — so the SPA's call, which carries the session cookie and no engine key, was answered `401 invalid_api_key`. - **Manual model entry for platforms with no static catalogue.** When a media provider has no static model list (`getModelsByProviderId` returns `[]`), the model selector did not render and `selectedModelId` stayed empty; `resolveQualifiedModel('')` then fell back to `provider.id` (`replicate`), which the backend rejects with `model "replicate" must be owner/name`. ### Providers & proxy
- **A provider+model pair can be parked as a unit, opt-in per provider.** Lockouts used to live only per connection (`modelLock_<model>` on the connection row), so when a combo member's quota was spent the failover walked the provider's remaining keys one at a time. A new fork-local table `providerModelLocks` can park `(provider, model)` as a single state with an absolute deadline: the combo skips the whole member instantly, the selector refuses every connection of that provider for that model, and a served request clears the park. **It is off for every provider by default** — the shape of a key pool is usually independent per-key quotas, and parking the pair there would strand healthy keys. A provider only opts in when its keys share one upstream quota, via `sharedQuotaProviders`. When opted in, only the quota class parks the pair: a 429 carrying a quota/capacity marker, a 402, or a 503 carrying a quota/capacity marker. A generic 429 stays a per-connection cooldown and a 401 stays a per-account park. The dashboard bell reports a pair lockout at pair scope with its deadline when one is recorded. *Deliberate divergence from `decolua/9router`, which has no pair-level park at all.*
- **Replayed reasoning fields are stripped for providers with a strict message validator.** Cerebras answered `400 ... property "messages.N.assistant.reasoning_content" is unsupported` for a conversation replayed from a reasoning model; `groq`, `mistral`, `kiro`, `kilocode` and `kilo-gateway` refuse the same fields (`reasoning_content`, `reasoning_details`, `reasoning`). The strip now runs on every forwarded body and on the OpenAI → Kiro `conversationState` translation, not only inside the opencode / DeepSeek / Kimi injection path. Providers that *require* the field are untouched.
- **CodeBuddy conversation identity follows the caller and the body.** A connection whose stored headers carry its own `X-Conversation-*` ids keeps them instead of being overwritten by a generated set — a differently-cased caller key and the generated header are one header once Go canonicalizes them, so which one survived was decided by map iteration order and the caller's conversation was silently restarted on an unpredictable subset of turns. The conversation key is now also read from the request body (`session_id`, `prompt_cache_key`, `conversation_id`) before falling back to the opening message, so turns whose first line differs stay in one conversation. Code `11128` is reported as the channel-verification failure it is — branched on the message, because the code also carries a body-shape error — instead of surfacing as a bare `400`. *Ported from `decolua/9router` #5217.*
